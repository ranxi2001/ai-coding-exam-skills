# 规范驱动开发（SDD）参考

## 核心定义

SDD（Spec-Driven Development，规范驱动开发或规格驱动开发）的核心是：先编写并商定一份详细、结构化的规范（Specification），再以此为“单一可信信息源”（Single Source of Truth）驱动整个开发过程。规范定义“做什么”（What）和“为什么做”（Why），代码则成为规范的实现产物，可以由人类或 AI 生成。

传统开发中，代码是最终真相，规范或文档往往事后补充并逐渐过时。SDD 反转了这一关系：规范是主要工件，代码是次要的、可再生的输出。这尤其适合 AI 生成代码的场景，因为模糊提示容易导致意图漂移、幻觉或不一致，而精确规范能提供稳定的上下文约束。

一句话概括：TDD 用可执行测试约束代码是否正确；SDD 用人机共读的规格约束实现是否忠于需求。

## 为什么适合 AI Coding

- AI 编码降低了实现门槛，但聊天式提示容易产生返工、架构偏离和安全问题。
- SDD 将隐式意图显式化，成为人、AI、产品和工程之间的共同契约。
- SDD 不替代 TDD/BDD，而是在实现阶段之前补充意图对齐。

## 规范成熟度

1. **Spec-first（规范先行）**：开发前先写规范；代码生成后不一定持续维护规范。
2. **Spec-anchored（规范锚定）**：规范与软件同步演进，变更时同步更新，并可配合自动检查。
3. **Spec-as-source（规范即源码）**：规范本身就是源代码，代码从规范生成或验证。

## 典型工作流

1. **Specify**：描述功能目标、用户故事、验收标准、范围边界、约束和非目标。
2. **Plan**：转化为技术设计，包括架构、数据流、接口和组件边界。
3. **Tasks**：拆解为可执行、可测试且相对独立的任务。
4. **Implement**：按任务生成代码、测试和文档，并对照规范验证。

常见文件：

- `proposal.md` / `requirements.md`：为什么做、目标和范围
- `spec.md`：行为契约和验收标准
- `design.md`：技术方案和架构设计
- `tasks.md`：具体实现步骤

## 与 TDD、BDD 和 Vibe Coding 的关系

| 方法 | 主要工件 | 作用层次 | 主要目标 |
| --- | --- | --- | --- |
| TDD | 可执行测试 | 函数/单元 | 防止回归 |
| BDD | Given-When-Then 场景 | 功能行为 | 跨角色对齐行为 |
| SDD | 结构化、可审查规范 | 系统意图与契约 | 约束 AI 输出、减少意图漂移 |
| Vibe Coding | 临时提示词 | 任意 | 快速探索，但容易失控 |

SDD 与 TDD/BDD 互补：SDD 先保证“建对的东西”，TDD 再保证“东西建对”。

## 工具与实践

- GitHub Spec Kit
- AWS Kiro
- OpenSpec
- Claude Code、Cursor、GitHub Copilot 等 AI 编码工具

## 优势与注意点

优势包括减少意图与实现差距、改善团队对齐、支持版本控制和审查，并适合复杂项目与企业治理。

注意点包括规范过细会增加前期成本；规范应是可演进的，而不是僵化的瀑布计划；规范质量直接决定输出质量。可以采用“人确定 What，AI 补充 How”的方式平衡成本。
