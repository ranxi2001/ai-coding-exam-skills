## 通用作答骨架

所有题目统一采用以下闭环：

1. 抄录环境、交付物和不可修改项。
2. 将 README 转为实体、契约、规则、验收四张清单。
3. 写 `spec.md`，固定字段名、状态、边界和非目标。
4. 按可独立验收的纵向功能块拆任务。
5. 先跑通一条最小主链，再补失败路径。
6. 让模型只写测试攻击当前实现，不同时修改业务代码。
7. 根据完整失败输出做最小修复，然后执行回归测试。
8. 每次测试全绿后建立版本 checkpoint。

## 题型一：多端早餐店订单系统

### 任务抽象

实现一个中心服务和三个终端：顾客下单端、店主处理端、订单展示端。订单按照题面规定的状态机流转，并支持权限校验、查询和完整交付。

### 真正考点

- 多客户端共享同一业务状态
- 显式状态机与非法跳转
- HTTP 契约和端口约定
- 店主操作权限
- 最小可用 TUI 与核心逻辑解耦
- 测试、启动说明和交付完整性

### 推荐最小架构

```text
models/state-machine
        |
repository -> service -> HTTP API
                         |-- customer client
                         |-- owner client
                         `-- display client
```

考试时间有限时，优先使用中心化 HTTP 服务和轮询。不要在题面没有要求时引入 WebSocket、消息队列、OAuth 或复杂前端。

### 实现顺序

1. 定义订单、订单项和状态枚举。
2. 用唯一迁移表实现所有状态变更。
3. 实现创建订单、查询订单、更新状态的最小 API。
4. 完成一条“下单 -> 确认 -> 制作 -> 取餐 -> 支付”的端到端测试。
5. 补非法跳转、终态修改、未知订单和权限失败。
6. 最后实现三个薄终端；界面只负责输入、调用 API 和展示。

### 高风险失分点

- 多个路由各自修改状态，导致规则不一致
- `READY` 可以被直接跳到，或终态仍可修改
- 权限只在客户端检查，服务端没有检查
- 端口、路径、响应字段和状态值与题面不一致
- TUI 做得很复杂，但核心 API 无法独立测试

### 必备测试

- 完整合法状态链
- 每个状态的所有非法下一状态
- 已取消、已支付订单不得再次推进
- 无 token、错误 token、正确 token
- 不存在的订单 ID
- 同一订单重复操作的题面规定行为

## 题型二：网页数据清洗管线

### 任务抽象

批量处理数千个结构、编码和质量不一致的 HTML 文件，提取商品名、价格、币种和库存等字段，输出稳定记录、错误明细和汇总统计。

### 真正考点

- 半结构化数据解析
- 字段归一化与稳定输出模型
- 单样本错误隔离
- 批处理可观测性
- 性能与确定性的取舍

### 推荐流水线

```text
discover -> read/decode -> parse -> normalize -> validate -> write/report
```

每个输入文件都必须产生可追踪结果。失败样本保留 `source_file`、稳定错误类型和原因，不能被静默丢弃。

### 实现顺序

1. 先固定统一输出结构和错误结构。
2. 实现稳定文件发现、排序和单文件处理接口。
3. 建立候选节点提取，再做价格、币种和库存归一化。
4. 用三个正常 HTML 变体跑通主链。
5. 补空文件、截断 HTML、非法编码、字段缺失和异常格式。
6. 数据正确后再考虑有限并发，并保证输出顺序和统计可复现。

### 高风险失分点

- 用巨大 `if/else` 绑定某几个页面结构
- 单个坏文件使整个批次退出
- 价格全部保留为字符串或丢失币种
- “有货/缺货”与数字库存混为一谈
- 并发写同一输出文件导致乱序或损坏
- 只输出成功数据，没有失败明细和统计

### 必备测试

- 多种 DOM 结构表达同一商品
- UTF-8、其他题面允许编码、非法字节
- 价格含千分位、货币符号、空格和单位
- 数字库存、有货、缺货、未知库存
- 空 HTML、截断 HTML、缺少必要字段
- 混合成功失败批次的统计守恒

## 题型三：LLM 批量推理控制台

### 任务抽象

读取 CSV，使用 `{列名}` 渲染 Prompt，通过 OpenAI 兼容接口或 Mock 模式批量推理，并在 CLI/TUI 中展示进度、错误和结果位置。

### 真正考点

- 外部模型接口抽象
- 模板契约和输入校验
- 批任务状态管理
- 超时、重试、失败隔离和结果恢复
- 无网络环境下的可测试性

### 推荐架构

```text
CSV reader -> template renderer -> task runner -> ModelClient
                                           |-- MockModelClient
                                           `-- OpenAICompatibleClient
           -> result store -> CLI/TUI view
```

`ModelClient` 必须统一成功、失败、超时和重试耗尽后的返回结构。Mock 至少能模拟成功、业务失败、超时、延迟和限流。

### 实现顺序

1. 固定任务记录、推理结果和错误结构。
2. 实现模板列名校验和单行渲染。
3. 使用 Mock 跑通 CSV 到结果文件的最小闭环。
4. 增加批次统计和单任务失败隔离。
5. 增加超时、有限重试和持续落盘。
6. 最后增加 TUI；核心 runner 必须脱离界面可测试。

### 高风险失分点

- 缺失模板列时静默替换为空字符串
- 响应 JSON 字段名靠模型猜测
- 单个请求失败导致整个批次崩溃
- 重试没有上限或把非重试错误反复重试
- API Key 写入代码、测试数据或日志
- TUI 显示完成，但结果尚未可靠写盘

### 必备测试

- 正常模板渲染和多列替换
- 模板引用不存在列
- CSV 空值、引号、换行和题面规定编码
- Mock 成功、失败、超时、限流后恢复
- 批次成功数、失败数、重试数与总数守恒
- 中途退出后的结果文件完整性

## 题型四：异构账单解析引擎

### 任务抽象

读取多机构、多产品、多 Sheet 的 Excel 账单，识别表头和明细，过滤汇总/备注行，完成机构、产品、金额、日期和数量归一化，输出结构化 JSON 与错误报告。

### 真正考点

- 动态表头与明细区域识别
- 配置化字段映射和别名归一化
- 金额、日期、数量的稳定类型
- 汇总行去重和可追溯性
- 局部失败继续处理

### 推荐流水线

```text
workbook reader -> sheet detector -> row classifier -> mapper
                -> normalizer -> validator -> JSON/error report
```

先定义统一内部模型，并保留 `source_file`、`source_sheet` 和源行号。机构别名和字段别名进入配置，不要散落在条件分支中。

### 实现顺序

1. 固定统一账单记录和错误记录结构。
2. 遍历所有 Sheet，并识别题面允许范围内的表头。
3. 区分明细、汇总、小计、备注和空行。
4. 实现字段映射与机构/产品别名归一化。
5. 实现金额、日期、数量解析和校验。
6. 用多 Sheet、不同表头位置和混合错误行验证。

### 高风险失分点

- 只读取第一个 Sheet
- 假定表头永远在第一行
- 汇总行和明细行重复计入金额
- 所有 JSON 值都输出为字符串
- 别名规则硬编码在解析主流程
- 某一行错误导致整个工作簿失败

### 必备测试

- 多 Sheet 且每个 Sheet 表头位置不同
- 机构简称、全称和未知机构
- 汇总、小计、备注和空行
- 金额含逗号、符号、空字符串和非法值
- 数量为整数、小数、带单位文本
- 缺关键字段时记录错误并继续处理

## 题型五：内存态治理与预算服务

### 任务抽象

实现一个内存态 HTTP JSON 服务，管理参与方、数据集版本、分析请求、预算账户和账本，并处理审批状态机、逻辑时间、幂等重放以及冻结/停用对在途请求的影响。

### 真正考点

- 长需求中的跨实体不变量
- 多对象原子变更
- 显式请求状态机
- 幂等重放与业务去重的区别
- 逻辑时钟和截止边界
- 预算锁定、消耗、释放与账本守恒

### 三条公共通道

1. **统一写入通道**：纯校验 -> 解析引用 -> 计算完整变更集 -> 原子提交。
2. **统一幂等通道**：作用域 + 幂等键 -> 请求指纹 + 首次完整响应。
3. **统一时间通道**：所有到期判断和事件推进只走一个逻辑时钟入口。

### 实现顺序

1. 基础设施：仓库、ID、错误结构、锁和 reset。
2. 公共通道：统一写入、幂等、逻辑时钟。
3. 参与方、数据集和版本。
4. 预算账户、锁定额和账本。
5. 一条提交 -> 审批 -> 完成/发布主链。
6. 拒绝、取消、过期、冻结和停用分支。
7. 查询、筛选、审计和统计。

### 高风险失分点

- 一边校验一边修改共享状态，失败后留下部分写入
- 多参与方预算逐个扣，最后一方不足时无法回滚
- 把相同幂等键的不同请求当作同一请求
- 业务去重只比较原始 JSON 字符串
- 使用系统真实时间而不是题面逻辑时钟
- 不同接口分别实现截止比较，产生 `<` 与 `<=` 不一致
- reset 漏清 ID、幂等索引、账本或派生缓存

### 必备测试

- 所有合法和非法状态迁移
- 任一依赖实体失效时，操作无副作用
- 多账户预算全部成功或全部失败
- 相同幂等键同请求重放、不同请求冲突
- 截止时刻前一刻、恰好截止、后一刻
- 时间跨越多个事件与禁止时间倒退
- 冻结、停用对新请求和在途请求的题面规定影响
- reset 后所有业务与辅助状态恢复初始值

## 补充题型：安全漏洞修复

修复 `pickle.load`、`exec`、Shell 注入、SQL 注入或硬编码密钥时，采用“定位输入边界 -> 构造攻击测试 -> 最小替换 -> 业务回归 -> 安全复扫”。详细参考 [security-repair.md](security-repair.md)。
