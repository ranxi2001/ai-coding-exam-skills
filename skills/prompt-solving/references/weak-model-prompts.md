# 低能力模型协作 Prompt 手册

目标不是让模型一次生成整个项目，而是把每轮任务压缩到它可以可靠完成和验证的范围。每个方括号都必须替换为当前题面的真实信息。

## Prompt 设计规则

1. 每轮只允许一个主要目标。
2. 明确允许修改和禁止修改的文件。
3. 原样写出字段名、状态值、路径、端口和启动命令。
4. 同时写“要做什么”和“不要做什么”。
5. 每轮给出可运行的验收命令或具体测试。
6. 要求模型先报告理解，再执行修改。
7. 测试生成和业务修复分成不同轮次。
8. 失败时粘贴完整命令、输出和相关需求，禁止只说“还是不对”。
9. 修复范围必须最小，并声明已通过行为不可破坏。
10. 连续三轮无进展时停止当前会话，用干净上下文重新开始。

## 第 1 轮：需求审计，不写代码

```text
完整阅读 README、现有代码、测试和配置。现在不要修改任何文件，也不要写实现。

请输出：
1. 环境清单：语言版本、入口、启动命令、端口、依赖和联网限制；
2. 契约清单：路径/参数/字段/类型/状态码/错误体，逐字保留题面命名；
3. 规则清单：状态迁移、精度、幂等、权限、失败副作用和边界；
4. 验收清单：每一项如何用命令或测试证明完成；
5. 歧义和假设：没有题面依据的地方只提问，不自行补规则；
6. 建议的最小主链和实现顺序。

最后列出最容易被隐藏测试检查的 10 个点。
```

## 第 2 轮：建立 SDD 工件

```text
根据刚才的需求审计创建或更新以下工件，但仍不要写业务实现：
- spec.md：目标、非目标、环境、精确契约、业务规则、边界和验收标准；
- design.md：最小架构、数据模型、状态机、模块边界和关键取舍；
- tasks.md：按可独立测试的纵向功能块拆分任务。

要求：
- 不得修改题面规定的命名；
- 不得加入题面未要求的生产级组件；
- 每个任务必须包含完成条件和验证命令；
- 标记必做、加分和明确不做项。

完成后只汇报三份文件的关键内容和仍未解决的歧义。
```

## 第 3 轮：只做最小闭环

```text
现在只实现以下最小闭环：[准确描述一条端到端路径]。

允许修改：[文件列表]
禁止修改：[题面文件、已有测试、其他稳定模块]

必须遵守：
- [精确入口/命令/路径/字段/状态]
- [本功能涉及的业务规则]
- [失败时必须保持不变的状态]

暂时不要实现：[加分项和旁支]

执行步骤：
1. 先列出计划修改的文件和原因；
2. 做最小实现；
3. 运行 [明确命令]；
4. 展示真实结果，不得仅声称通过；
5. 若失败，先报告根因，不要扩大修改范围。
```

## 第 4 轮：只生成攻击测试

图片材料中最值得保留的技巧就是这一轮：让模型根据需求攻击刚完成的代码，但禁止它顺手修改实现。

```text
逐条对照 spec.md、README 和当前实现，新增一组可直接运行的测试。

现在只写测试，先不要改我的业务代码。

覆盖：
- 正常主链；
- 缺字段、错误类型、空值和边界值；
- 非法状态迁移和终态操作；
- 重复请求或幂等行为；
- 失败操作无副作用；
- 精确响应字段名、字段类型、状态码或退出码；
- README 已明确但当前实现可能遗漏的规则。

先输出“需求条目 -> 测试用例”的对应表，再写测试并运行。
不要降低断言，不要删除既有测试，不要为了让测试通过而改变测试目标。
```

## 第 5 轮：用失败证据做最小修复

```text
以下测试失败：
[粘贴完整测试命令]
[粘贴完整失败输出]

对应需求：
[粘贴 README/spec 原文]

先回答：
1. 实际行为和期望行为分别是什么；
2. 根因位于哪个文件、函数和规则；
3. 你的最小修复范围是什么。

然后实施最小修复。已经通过的逻辑不要动，不做无关重构，不改字段名、公开接口和测试。

修复后依次运行：
1. 当前失败测试；
2. 同功能的边界测试；
3. 全量回归测试。

最后报告改动、真实测试结果和仍未覆盖的风险。
```

## 第 6 轮：协议逐字审计

弱模型常见的致命问题不是业务推理，而是擅自重命名。用这一轮单独检查协议。

```text
逐项比较 README/spec 与当前实现，只检查契约一致性，不新增功能。

检查：
- 入口文件、启动命令、监听地址和端口；
- HTTP 方法、路径和参数位置；
- JSON 字段名、大小写、层级、类型和空值表现；
- 状态枚举、错误码、HTTP 状态码；
- CLI 参数、stdout/stderr、退出码和输出文件名。

输出差异表：题面要求 | 当前实现 | 是否一致 | 最小修复。
只修复确定不一致的项目，然后运行契约测试和全量回归。
```

## 第 7 轮：卡住后的干净会话交接

```text
你接手一个尚未完成的限时 AI Coding 项目。不要沿用之前的猜测。

唯一依据：
- README/spec：[路径]
- 当前稳定版本：[commit 或快照标识]
- 已通过测试：[命令和结果摘要]
- 唯一待解决问题：[一句话]
- 复现命令：[完整命令]
- 完整失败输出：[原样粘贴]

先独立定位根因并给出一个最小修复方案。禁止重写项目、升级依赖、改公开契约或修改已通过测试。得到确认后再改代码。
```

## 第 8 轮：提交前验收

```text
按 README/spec 做提交前审计。不要新增功能，只修复会阻止启动、破坏契约或导致现有测试失败的问题。

1. 从干净环境执行指定安装和启动命令；
2. 执行一条真实端到端主链；
3. 运行完整测试和题面要求的静态检查；
4. 检查字段、状态、端口、文件名、退出码和输出格式；
5. 检查密钥、Token、调试日志和临时文件；
6. 对照验收清单逐项给出证据。

最终输出：已完成项、未完成项、测试命令与结果、已知问题、运行方式、交付文件清单。不要编造不存在的功能。
```

## 版本管理协议

在考试允许使用 Git 时：

1. 修改前确认 `git status --short`，识别题目初始文件和已有改动。
2. 首次可运行时建立 `checkpoint: minimal runnable`。
3. 每完成一个功能块且相关测试与回归全绿，建立一个 checkpoint。
4. 测试变少、主链损坏或模型开始大范围重构时，停止继续叠补丁。
5. 先查看当前 diff，回到最近稳定 checkpoint 后再做更小修改。

考试禁止提交或仓库没有 Git 时，用 IDE snapshot 或复制少量关键文件建立等价 checkpoint。不要用一个旧文件覆盖整个项目，也不要回退题目方原始文件。

推荐 checkpoint 语义：

```text
checkpoint: baseline inspected
checkpoint: minimal runnable
checkpoint: order flow green
checkpoint: boundary tests green
checkpoint: final acceptance
```
